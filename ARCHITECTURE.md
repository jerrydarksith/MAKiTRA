# Архітектура проєкту

## Призначення

Це персональна система збереження інформації. Telegram є лише зовнішнім
інтерфейсом. Бізнес-правила не залежать від `python-telegram-bot`.

## Цільова структура першого етапу

```text
src/personal_bot/
├── __main__.py                 # Точка входу
├── bootstrap.py                # Збирання та явне підключення модулів
├── config.py                   # Завантаження налаштувань із .env
├── core/                       # Спільні доменні моделі, enum-и, помилки
├── db/
│   ├── database.py             # Єдиний клас, що працює з sqlite3
│   ├── schema.py               # Початкове створення таблиць
│   └── repositories/           # По одному репозиторію на сутність
├── access/                     # Майбутні авторизація й заявки
├── categories/                 # Майбутня бізнес-логіка категорій
├── settings/                   # Майбутня логіка налаштувань
└── telegram/
    └── menus/                  # По одному файлу на меню
```

Реалізовані тільки модулі, потрібні для SQLite та мінімальної команди `/start`.
Категорії, налаштування й меню адміністратора з'являтимуться разом із першим
кодом, який їх використовує: код "про запас" не додається.

## Взаємодія шарів

```text
Telegram handler -> Service -> Repository -> Database -> SQLite
```

- Handler приймає Telegram-подію, передає прості дані в сервіс і показує
  результат користувачу.
- Service містить бізнес-правила та не імпортує Telegram-типи.
- Repository виконує запити лише через `Database`.
- Лише `Database` імпортує та використовує `sqlite3`.
- `Database.transaction()` атомарно фіксує зміни або повністю їх скасовує.

## Початкова структура бази даних

### `users`

Авторизовані користувачі: Telegram ID, дані профілю, номер, роль, статус і
дати створення/оновлення. `telegram_id` є унікальним ідентифікатором.

Ролі: `super_admin`, `admin`, `user`.

Статуси створеного користувача: `active`, `blocked`. Стан `pending` належить
заявці, бо користувач створюється тільки після схвалення.

### `access_requests`

Незмінна історія заявок. Вона містить знімок Telegram-даних, номер телефону,
стан (`pending`, `approved`, `rejected`) і дані про розгляд. Частковий
унікальний індекс гарантує лише одну `pending`-заявку для одного `telegram_id`.

### `user_settings`

Один запис на користувача: часовий пояс, валюта, формат дати, мова та дата
оновлення.

### `categories`

Особисте дерево категорій: власник, необов'язкова батьківська категорія, назва,
іконка та дати. Категорії не є бізнес-сутностями, зокрема автомобілями.

У сервісі категорій буде обов'язкова перевірка, що батьківська категорія має
того самого власника. SQLite-зовнішній ключ не може виразити цю складену
вимогу без надмірного ускладнення схеми.

## Авторизація: поточна поведінка

1. Telegram ID — головний ідентифікатор.
2. Команда `/start` шукає користувача за Telegram ID.
3. Невідомому користувачу показується кнопка надсилання власного номера.
4. Лише contact із `contact.user_id`, що збігається з Telegram ID відправника,
   приймається як підтвердження номера.
5. Перший користувач після створення порожньої БД стає `super_admin`, а його
   `users` і `user_settings` створюються в одній транзакції.
6. Для наступного користувача створюється одна pending-заявка; повторне
   надсилання контакту не створює дубліката.
7. Усі активні Super Admin отримують повідомлення з даними заявки та кнопками
   схвалення або відмови.
8. Callback передає рішення в `AccessService`, який повторно перевіряє роль
   Super Admin і статус заявки.
9. Схвалення створює `users` і `user_settings`, а також позначає заявку
   `approved` в одній транзакції.
10. Відмова позначає заявку `rejected`; після цього користувач може подати нову.
11. Користувачеві зі статусом `active` показується головне меню.
12. Користувачеві зі статусом `blocked` показується повідомлення про блокування.

## Ізоляція даних

Кожен запит до категорій та майбутніх особистих сутностей обов'язково фільтрує
дані за `owner_user_id`. Це унеможливлює доступ до чужих записів через callback
або навмисно змінені параметри. Запити до `users` і `access_requests` є
винятком: вони працюють за Telegram ID або правами Super Admin, бо не мають
поля власника.

## Додавання нового модуля

Новий модуль створюється в окремій папці, наприклад `vehicles/`. У ній будуть
його сервіс, Telegram handlers і, за потреби, папка `repositories/`. Меню
створюється окремим файлом у `telegram/menus/`. Єдина зміна наявного коду —
явне підключення нового модуля у `bootstrap.py`.

Автоматичне виявлення модулів, plugin system і feature loader не
використовуються.

## Остаточне архітектурне рішення для модуля records

### Мета

Модуль `records` має стати універсальним шаром для зберігання різних типів
записів у папках дерева MakiTra. Він повинен підтримувати повний життєвий цикл
запису: створення, перегляд, редагування, видалення й повернення до папки.
При цьому архітектура має залишатися простою, зрозумілою та легко
розширюваною.

### Основні принципи

1. Telegram залишається лише інтерфейсом.
2. Бізнес-логіка знаходиться у сервісах.
3. Репозиторії працюють лише через `Database` і SQLite.
4. Жоден сервіс не повинен знати про конкретні типи записів.
5. Кожен тип запису є окремим модулем.
6. Додавання нового типу має вимагати лише створення нового модуля,
   реалізації контракту й реєстрації у Registry.
7. Усі специфічні дані зберігаються лише у полі `payload`.
8. Типи записів є частиною програмного коду, а не користувацькими даними.

### 1. Структура таблиці `records`

Для MVP достатньо однієї таблиці `records`.

Поля:
- `id` — первинний ключ;
- `owner_user_id` — власник запису;
- `folder_id` — папка, у якій знаходиться запис;
- `type` — код типу, наприклад `short_text`, `amount`, `date`, `phone`;
- `name` — назва запису;
- `payload` — JSON з типоспецифічними даними;
- `sort_order` — порядок відображення у папці;
- `created_at` — дата створення;
- `updated_at` — дата останнього оновлення;
- `preview_text` — необов’язкове поле для зручного відображення в списках.

Ця схема є достатньою для MVP і не вимагає окремої таблиці типів.

### 2. Формат `payload`

Усі специфічні дані зберігаються лише у полі `payload` у форматі JSON.

Приклади:
- короткий текст: `{ "value": "Привіт" }`
- число: `{ "value": 42 }`
- сума: `{ "amount": 1200, "currency": "UAH" }`
- дата: `{ "value": "2026-07-27" }`
- так/ні: `{ "value": true }`
- посилання: `{ "url": "https://example.com" }`
- список: `{ "value": "home", "options": ["home", "work"] }`

Це дає однорідний формат зберігання для всіх типів і не ускладнює схему БД.

### 3. Структура Registry

Registry є єдиною точкою знання про доступні типи записів.

Він має містити:
- карту `type_code -> type implementation`;
- метод `register(type_code, implementation)`;
- метод `get(type_code)`;
- метод `list_available_types()`.

Registry створюється один раз під час запуску застосунку в `bootstrap.py` і
після ініціалізації не змінюється. Він не підтримує динамічну реєстрацію,
plugins або інші форми runtime-модифікації. Registry є лише статичним
відображенням `type -> implementation`.

RecordsService не повинен імпортувати глобальний Registry. Registry
передається в сервіс як звичайна залежність під час створення сервісу.

Жоден сервіс не повинен знати про конкретні типи вручну. Сервіс працює лише
через Registry.

### 4. Контракт типу запису

Кожен тип запису повинен реалізувати один і той самий контракт.

Рекомендований контракт:
- `create_initial_data()` — підготовка початкового стану для створення;
- `validate(payload)` — перевірка введених даних;
- `serialize(data)` — перетворення даних у формат для збереження;
- `deserialize(payload)` — читання з БД у внутрішній формат;
- `render(payload)` — текстове представлення для перегляду;
- `preview(payload)` — короткий текст для списку або попереднього перегляду;
- `build_editor_steps()` — кроки створення/редагування для конкретного типу.

Назви можуть бути трохи змінені, але суть контракту має залишитися такою:
один тип = одна реалізація = одна логіка створення/редагування/перегляду/валідації.

Кожен тип запису є єдиним власником структури свого payload і сам відповідає
за його валідацію, серіалізацію та десеріалізацію.

### 5. Організація модуля `records`

Рекомендована структура каталогів:

```text
src/personal_bot/
  records/
    __init__.py
    service.py
    callback_handlers.py
    message_handlers.py
    repositories/
      record_repository.py
    types/
      __init__.py
      base.py
      short_text.py
      long_text.py
      number.py
      amount.py
      date.py
      datetime.py
      period.py
      boolean.py
      url.py
      phone.py
      email.py
      choice.py
    registry.py
```

#### `service.py`

Головний сервіс модуля. Він координує:
- створення запису;
- редагування;
- перегляд;
- видалення;
- валідацію;
- збереження в репозиторій.

#### `repositories/record_repository.py`

Виконує CRUD-операції над таблицею `records`.

Відповідальність:
- створити запис;
- отримати запис за id і власником;
- отримати список записів у папці;
- оновити запис;
- видалити запис;
- повернути наступний `sort_order`.

#### `registry.py`

Зберігає доступні типи й делегує їм роботу через контракт.

#### `types/`

Кожен тип має власний модуль. Наприклад:
- `short_text.py` — логіка короткого тексту;
- `amount.py` — логіка суми і валюти;
- `choice.py` — логіка вибору одного значення із набору.

Модулі `records/types` не повинні залежати від Telegram, Database, SQLite або
Repository. Вони працюють лише зі звичайними Python-даними.

### 6. Життєвий цикл запису

Усі типи мають однаковий життєвий цикл.

Папка
↓
➕ Новий запис
↓
Вибір типу
↓
Створення
↓
Перегляд
↓
Редагування
↓
Видалення
↓
Повернення до папки

Тип впливає лише на внутрішню логіку створення, редагування та відображення.
Саме життя запису залишається однаковим для всіх типів.

### 7. Процес створення запису

Процес має бути покроковим і не залежати від Telegram-деталей.

Під час створення, читання, оновлення та видалення записів обов'язково
перевіряється:
- запис належить `owner_user_id`;
- `folder_id` належить тому самому `owner_user_id`.

1. Користувач натискає `➕ Новий запис`.
2. Handler показує список доступних типів.
3. Користувач обирає тип.
4. RecordsService звертається до Registry.
5. Registry повертає реалізацію типу.
6. Тип повертає перший крок створення.
7. Handler зберігає стан чернетки користувача.
8. Наступні відповіді користувача обробляються в тому самому сценарії.
9. Після завершення сервіс зберігає запис у БД.

Для MVP це може бути простий state machine у handler або сервісі.

### 8. Процес редагування

Редагування має йти за тим самим сценарієм, але з уже існуючим записом.

1. Користувач відкриває запис.
2. RecordsService отримує запис з репозиторію.
3. Через Registry визначається реалізація типу.
4. Тип підготовлює дані для редагування.
5. Користувач змінює значення.
6. Після підтвердження сервіс зберігає оновлений запис.

### 9. Процес перегляду

1. RecordsService отримує запис з репозиторію.
2. Через Registry визначається тип.
3. Тип формує текст для відображення користувачу.
4. Telegram handler показує цей текст з відповідною клавіатурою.

### 10. Процес видалення

1. Користувач відкриває запис.
2. Система показує підтвердження видалення.
3. Після підтвердження репозиторій видаляє запис за `id` і `owner_user_id`.
4. Користувач повертається до перегляду папки.

### 11. Додавання нового типу запису

Додавання нового типу має бути максимально простим.

Потрібно лише:
1. створити новий файл у `records/types/`;
2. реалізувати контракт типу;
3. зареєструвати тип у Registry;
4. не змінювати існуючі типи.

Це відповідає принципу відкритості для розширення і закритості для зміни.

### 12. Відповідність SOLID без надмірного ускладнення

Ця архітектура добре узгоджується з основними принципами SOLID, але без
перетворення на надмірну абстракцію.

- Single Responsibility: кожен тип відповідає лише за себе;
- Open/Closed: новий тип додається без змін старих типів;
- Liskov Substitution: всі типи реалізують один контракт;
- Interface Segregation: контракт є простим і достатнім;
- Dependency Inversion: сервіси залежать від Registry, а не від конкретних типів.

### 13. Слабкі місця й можливі покращення

Основне слабке місце цього підходу — менша строгість даних на рівні БД,
оскільки значення зберігаються у `payload` як JSON. Це прийнятно для MVP і для
довгострокового розвитку, але в майбутньому можна розширити архітектуру
додатковими правилами валідації або схемами JSON для окремих типів.

Можливі покращення в майбутньому:
- додати валідацію на рівні схем JSON для кожного типу;
- ввести простий механізм версій `payload`, якщо змінюватимуться формати даних;
- додати кешування або індекси для частих запитів по папках і датах.

### 14. Чому це найкраще підходить для довгострокового розвитку MAKiTra

Ця архітектура є оптимальним балансом між простотою і розширюваністю.

Вона підходить для MAKiTra, бо:
- не вводить зайву складність у MVP;
- не потребує ORM і складної схеми БД;
- добре узгоджується з існуючою layered architecture;
- дозволяє легко додавати нові типи записів без переписування старого коду;
- зберігає код зрозумілим навіть через кілька років розвитку проєкту.

### Короткий висновок

Остаточне рішення для records таке:
- одна таблиця `records`;
- поле `type` для коду типу;
- поле `payload` для всіх типоспецифічних даних;
- окремі модулі типів у `records/types/`;
- Registry як єдина точка знання про типи;
- однаковий життєвий цикл для всіх записів.

Це рішення є простим, достатнім для MVP і достатньо масштабованим для
майбутнього розвитку MAKiTra без надмірного ускладнення.

## Правила розробки

- Класи, методи, функції, змінні та файли називаються англійською без
  неочевидних скорочень.
- Повідомлення користувачу пишуться українською.
- Один файл має одну відповідальність.
- Не додавати абстракції, код або залежності, які не потрібні зараз.
- Не дублювати логіку; повторюваний код потрібно винести після окремого
  погодження, якщо це впливає на архітектуру.
- Нові залежності потребують попереднього пояснення й підтвердження.
- Нова схема БД у майбутньому вимагатиме окремого погодженого рішення щодо
  оновлення вже наявних баз даних.
