## 1. Поточна архітектура проєкту

Проєкт побудований за шаровою архітектурою з чітким поділом на:

1. Telegram layer
   - обробники команд і повідомлень;
   - меню та inline-кнопки;
   - інтеграція з бібліотекою python-telegram-bot.

2. Service layer
   - бізнес-логіка доступу;
   - перевірка ролей, статусів, створення заявок і користувачів.

3. Repository layer
   - доступ до даних через SQL-запити;
   - абстрагування роботи з базою від бізнес-логіки.

4. Persistence layer
   - єдиний клас для роботи з SQLite;
   - схема БД і транзакції.

### Основна ідея архітектури
- Telegram є лише зовнішнім інтерфейсом.
- Бізнес-логіка не залежить від Telegram.
- Репозиторії не містять бізнес-правил.
- База даних працює через єдиний клас Database.

### Архітектурний потік

Telegram handler -> Service -> Repository -> Database -> SQLite

## 2. Опис кожного модуля

### Кореневий пакет: src/personal_bot

> Примітка: у довгостроковій концепції центральним ядром системи виступає не Records, а Objects. Це не змінює поточну реалізацію, а лише уточнює напрямок подальшого розвитку.

#### __main__.py
- Точка входу застосунку.
- Запускає bootstrap.run_application().
- Ловить ValueError і друкує повідомлення користувачу.

#### bootstrap.py
- Центр складання застосунку.
- Ініціює підключення конфігурації, бази даних, репозиторіїв, сервісу доступу та Telegram-application.
- Збирає основні компоненти в єдиному місці.

#### config.py
- Завантажує конфігурацію з .env.
- Витягує TELEGRAM_BOT_TOKEN і DATABASE_PATH.
- Повертає об’єкт ApplicationSettings.

### Пакет access

#### service.py
- Основний сервіс доступу.
- Відповідає за реєстрацію контакту, створення першого Super Admin, створення pending-заявок, схвалення та відхилення заявок.
- Використовує транзакції для атомарних змін.

#### start_command_handler.py
- Обробляє команду /start.
- Визначає, чи користувач вже є в системі, чи заблокований, чи повинен подати заявку.
- Формує відповідні повідомлення та клавіатуру.

#### contact_message_handler.py
- Обробляє Telegram-contact.
- Перевіряє, що номер надіслано саме від цього користувача.
- Передає контакт у AccessService.
- Повідомляє користувача про результат реєстрації або заявки.

#### access_request_notification_sender.py
- Відправляє повідомлення Super Admin про нову заявку.
- Форматує текст заявки.
- Додає inline-клавіатуру для схвалення/відмови.

#### callback_handlers/access_request_callback_handler.py
- Обробляє callback-запити від inline-кнопок.
- Розпізнає action approve/reject.
- Передає рішення до AccessService і відправляє користувачу відповідь.

### Пакет core

#### entities/access_request.py
- Модель заявки на доступ.

#### entities/user.py

### Пакет db

#### database.py
- Єдиний клас для роботи з SQLite.

#### schema.py
- Ініціалізує початкову схему бази даних.

#### repositories/user_repository.py

#### repositories/access_request_repository.py

- Реалізує створення pending-заявки, перевірку наявності pending, пошук за ID, позначення як reviewed.

#### repositories/settings_repository.py
- Репозиторій для налаштувань користувача.

### Пакет telegram

## 3. Опис кожного сервісу

### AccessService
**Призначення**
- Головний сервіс доступу в системі.
- Централізує логіку реєстрації, перевірки прав, створення заявок і їх обробки.

**Відповідальність**
- знаходити користувача за Telegram ID;
- створювати першого Super Admin;
- створювати pending-заявку для наступного користувача;
- схвалювати заявку;
- відхиляти заявку;
- перевіряти, чи користувач є активним Super Admin.

**Особливості**
- Використовує транзакції через Database.transaction().
- Не залежить від Telegram API безпосередньо.
- Зберігає бізнес-правила в сервісі, а не в handlers.

### AccessRequestNotificationSender
**Призначення**
- Сервісоподібний компонент для відправлення повідомлення Super Admin про нову заявку.

**Відповідальність**
- надсилати повідомлення кожному активному Super Admin;
- форматувати текст заявки;
- прикріплювати inline-клавіатуру review menu.

## 5. Потік виконання від /start до роботи з базою

### Scenario 1: користувач надсилає /start
1. Telegram отримує команду /start.
2. StartCommandHandler.handle() отримує Update і ефективного користувача.
3. Handler звертається до AccessService.find_user_by_telegram_id(telegram_id).
4. AccessService делегує запит UserRepository.find_by_telegram_id.
5. UserRepository виконує SELECT до таблиці users через Database.execute().
6. Якщо користувач не знайдений — відправляється повідомлення про необхідність подати заявку.
7. Якщо користувач існує й активний — відправляється головне меню.

### Scenario 2: користувач надсилає контакт
1. ContactMessageHandler.handle() отримує Update з contact.
2. Handler перевіряє, що контакт належить саме цьому користувачу.
3. Якщо перевірка пройдена — викликається AccessService.register_contact(...).
4. AccessService відкриває транзакцію через Database.transaction().
5. AccessService перевіряє:
   - чи користувач вже зареєстрований;
   - чи це перший користувач у системі;
   - чи вже є pending-заявка.
6. У разі створення нового Super Admin:
   - UserRepository.create(...)
   - SettingsRepository.create_default(...)
   - коміт транзакції.
7. У разі створення заявки:
   - AccessRequestRepository.create_pending(...)
   - UserRepository.find_active_super_admins()
   - повідомлення надсилаються Super Admin.
8. Репозиторії працюють через Database.execute() / Database.execute_script().
9. Database застосовує BEGIN IMMEDIATE, COMMIT або ROLLBACK.

### Scenario 3: Super Admin схвалює або відхиляє заявку
1. Callback handler отримує callback_data.
2. AccessRequestCallbackHandler передає рішення до AccessService.
3. AccessService перевіряє права Super Admin і статус заявки.
4. У разі схвалення:
   - створюється користувач;
   - створюються default settings;
   - заявка позначається як approved.
5. У разі відхилення:
   - заявка позначається як rejected.
6. Усі зміни виконуються в транзакції.

## 7. Сильні сторони архітектури

1. Чітке розмежування шарів
   - handlers, service, repositories, database.

2. Відокремлення бізнес-логіки від Telegram
   - AccessService не залежить від python-telegram-bot.

3. Єдиний доступ до БД
   - Database є єдиною точкою роботи з SQLite.

4. Транзакції підтримуються на рівні сервісу
   - критичні операції виконуються атомарно.

5. Наявність тестів
   - є покриття для основного access-flow, транзакцій, схеми БД і валідації контакту.

6. Простота розуміння
   - архітектура не перевантажена абстракціями.

---

## 8. Слабкі сторони архітектури

1. Поки що відсутній повноцінний DI-контейнер
   - bootstrap зберігає багато явних залежностей.

2. Сервіс має занадто багато відповідальностей
   - AccessService одночасно керує реєстрацією, правами, заявками й створенням користувачів.

3. Telegram-логіка та бізнес-логіка частково змішані
   - handlers формують частину поведінки користувача, але не тільки обробляють події.

4. Відсутність явних domain exception-ів
   - помилки обробляються через повернення результатів, а не через винятки.

5. Частина модулів не реалізована
   - users/service.py і users/callback_handlers.py порожні.

6. Меню й повідомлення формуються прямо в handlers/menus
   - це може стати складним для розширення.

7. Залежність від конкретних репозиторіїв у сервісі
   - зростання кількості функціональності підвищить складність конструктора сервісу.

## 9. Технічний борг

1. Порожній модуль users
   - архітектурно підготовлений, але не функціональний.

2. Повторення логіки створення користувача й налаштувань
   - однакові кроки повторюються в кількох сценаріях.

3. Повторюваний мапінг з SQL-рядків у об’єкти
   - у репозиторіях є багато подібних конструкцій.

4. Обмежена обробка помилок
   - відсутня централізована модель помилок і обробки виключень.

5. Відсутність міграцій БД
   - змінювати схему без ручного контролю буде складно.

6. Обмежені межі відповідальності для handlers
   - при рості кількості команд і сценаріїв handlers можуть стати надто великими.

## 10. Потенційні проблеми при масштабуванні

### Концептуальні ризики
- Перехід від окремих модулів до єдиної моделі Objects потребуватиме чіткого узгодження структури даних.
- Якщо різні модулі будуть розвиватися як незалежні сутності, може виникнути дублювання логіки замість роботи через спільне ядро.
- Без чіткої ролі Objects як центральної моделі система ризикує перетворитися на набір несумісних підмодулів.

1. Зростання кількості функцій у AccessService
   - сервіс може стати “god object”.

2. Ускладнення маршрутизації Telegram-інтеракцій
   - з ростом команд і меню handlers стануть менш керованими.

3. Потреба в багатьох репозиторіях і нових таблицях
   - без більш чіткої структури складність зросте швидко.

4. Складність підтримки схеми БД
   - без міграцій і версіонування схема стане джерелом регресій.

5. Ризик дублювання логіки в нових модулях
   - якщо кожен новий модуль буде розвиватися без загальних патернів, код швидко розростеться.

6. Обмежена тестова покритість для handlers і Telegram-інтеграції
   - бізнес-логіка покрита, але інтеграційні сценарії ще не охоплені повністю.

## 11. Рекомендації (без змін у коді)

- Зберегти Objects як центральну концепцію системи для майбутнього розвитку.
- Розвивати модулі Users, Categories і Objects як фундаментальні шари.
- Поступово інтегрувати Finance, Notes, Vehicles, Assets, Documents і Statistics поверх спільного ядра Objects.
- Уникати створення окремих паралельних моделей для схожих сутностей.
- Підтримувати простоту розвитку і не вводити складні абстракції до моменту, коли вони реально потрібні.

1. Зберігати поточний шаровий підхід, але розширити його структурно
   - не зламуючи існуючий розподіл відповідальності.

2. Поступово виділяти окремі підсервіси в межах current domain
   - наприклад, для створення користувача, обробки заявок і роботи з налаштуваннями.

3. Розширити модуль users
   - як наступний логічний крок після access-flow.

4. Підвищити рівень абстракції для роботи з помилками
   - через явні exception-типи або централізовану обробку в handlers/service.

5. Підготувати підґрунтя для міграцій БД
   - навіть без впровадження зараз, це варто планувати.

6. Збільшити роль інтеграційних тестів
   - особливо для Telegram-обробників і сценаріїв з callback-ом.

7. Продовжувати зберігати простоту
   - не додавати складних абстракцій без потреби, бо саме ця властивість є сильним боку поточної реалізації.

## Підсумок

Проєкт вже має зрозумілу базову архітектуру і працює в межах своєї поточної задачі. Основна сила полягає в тому, що він дотримується простого й послідовного шарового підходу. Основні слабкості пов’язані не з відсутністю структури, а з тим, що архітектура ще не повністю розгорнута для майбутніх модулів і масштабування.
