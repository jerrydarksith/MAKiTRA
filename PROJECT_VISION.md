# PROJECT_VISION

## 1. Головна ідея проєкту

MAKiTRA — це не Telegram-бот, а персональна система управління інформацією для одного користувача або невеликої команди. Її мета — стати єдиним місцем для зберігання, організації, пошуку та використання різних типів особистих даних.

Основна ідея полягає в тому, що користувач має отримати впорядкований цифровий простір, де:
- інформація зберігається структуровано;
- доступ до неї відбувається через зручний інтерфейс;
- бізнес-логіка не залежить від конкретного каналу взаємодії;
- система з часом може розширюватися новими модулями без руйнування існуючого ядра.

MAKiTRA має бути системою, яка допомагає не просто «зберігати дані», а реально управляти ними: групувати, пов’язувати, шукати, відстежувати й аналізувати.

---

## 2. Основні принципи

### 2.1. Telegram лише як UI
Telegram є лише одним із можливих інтерфейсів. Він не повинен визначати модель даних, правила бізнес-логіки чи структуру домену.

### 2.2. Бізнес-логіка незалежна від інтерфейсу
Основні сценарії роботи мають реалізовуватися незалежно від того, де користувач взаємодіє з системою: у Telegram, веб-інтерфейсі, API або командному інтерфейсі.

### 2.3. Дані незалежні від інтерфейсу
Вся інформація має зберігатися в загальній моделі даних, яку можна використовувати незалежно від UI.

### 2.4. SQLite — стартовий рівень, а не остаточне обмеження
На початковому етапі SQLite є достатнім для локальної та простої роботи. У майбутньому система повинна залишатися відкритою для заміни сховища даних без повної переписування логіки.

### 2.5. Кожен модуль має власну логіку, але спільне ядро
Кожен функціональний блок повинен мати свою область відповідальності, але всі вони мають працювати в рамках єдиної системи прав, категорій, об’єктів і налаштувань.

### 2.6. Простота понад надмірну абстракцію
Система повинна розвиватися поступово. Важливо не ускладнювати архітектуру без потреби.

### 2.7. Пріоритет — реальна користь
Функціональні модулі мають з’являтися там, де вони реально допомагають користувачу управляти інформацією, а не просто через технічну цікавість.

## Архітектурні правила

- Telegram є лише UI.
- Вся бізнес-логіка знаходиться в сервісах.
- Репозиторії не містять бізнес-логіки.
- Один модуль = одна зона відповідальності.
- Objects є центральною моделлю системи.
- Нові модулі не повинні дублювати існуючу логіку.
- Простота важливіша за складні абстракції.
- Передчасний рефакторинг заборонений.

## 3. Великі модулі

Нижче наведено основні великі напрямки розвитку MAKiTRA.

### Users
Модуль користувачів і доступу. Включає:
- профілі користувачів;
- ролі й права;
- статуси аккаунтів;
- авторизацію та доступ до функцій.

### Categories
Модуль категорій. Відповідає за:
- ієрархічну структуру категорій;
- групування інформації;
- налаштування зв’язків між різними типами даних.

### Objects
Центральний модуль системи. Він описує універсальну модель будь-якого об’єкта: автомобіль, документ, людина, квартира, ноутбук, фінансова операція, нотатка тощо. Кожен об’єкт має:
- власні властивості;
- категорії;
- пов’язані дані;
- можливість бути спеціалізованим або базовим елементом системи.

Objects є основою для інших модулів, оскільки дозволяє працювати з різними сутностями через одну універсальну модель.

### Finance
Модуль фінансів. Передбачає:
- рахунки;
- витрати;
- доходи;
- регулярні платежі;
- звітність.

### Assets
Модуль активів. Може охоплювати:
- матеріальні цінності;
- цифрові ресурси;
- посилання, документи, товари або інші об’єкти.

### Vehicles
Модуль транспортних засобів. Може включати:
- дані про авто;
- технічне обслуговування;
- документи;
- витрати на експлуатацію.

### Notes
Модуль нотаток. Призначений для:
- особистих заміток;
- довгострокових думок;
- тез, планів і контексту.

### Tasks
Модуль задач. Містить:
- завдання;
- підзадачі;
- дедлайни;
- статуси прогресу;
- нагадування про виконання.

### Reminders
Модуль нагадувань. Відповідає за:
- нагадування про події;
- повторювані напоминання;
- часові тригери.

### Statistics
Модуль статистики. Потрібен для:
- підсумків по діяльності;
- аналітики по витратах, записах, задачах;
- звітів і діаграм.

### Documents
Модуль документів. Може працювати як сховище для:
- файлів;
- сканів;
- важливих документів;
- пов’язаних записів.

### Settings
Модуль налаштувань. Включає:
- особисті переваги;
- мову;
- часовий пояс;
- формат дати;
- зовнішній вигляд інтерфейсу;
- глобальні параметри поведінки системи.

## 4. Залежності між ними

Модулі MAKiTRA мають розвиватися як єдина екосистема, але з чіткими зв’язками.

### Базові модулі
- Users — фундамент для доступу, ролей і ідентифікації користувача.
- Categories — фундамент для структурування інформації.
- Objects — фундамент для універсального опису будь-якої сутності.
- Settings — загальний модуль для поведінки системи.

### Залежності між модулями
- Finance використовує Objects.
- Assets використовує Objects.
- Vehicles використовує Objects.
- Notes використовує Objects.
- Documents використовує Objects.
- Tasks можуть бути спеціалізованими Objects.
- Reminders можуть працювати поверх Tasks, Objects і Settings.
- Statistics використовує Objects, Finance, Tasks, Notes і Assets.
- Users є базовим модулем для всіх інших, оскільки визначає доступ і контекст користувача.
- Categories забезпечує структурування для Objects і всіх модулів, що будуються на них.

### Принцип зв’язків
Залежності мають бути смисловими, а не технічними. Модуль не повинен залежати від UI або від конкретного каналу взаємодії.

---

## 5. Які модулі є фундаментом

Фундамент MAKiTRA складають три основні напрямки:

### Users
Без цього модуля не існує контексту користувача, прав доступу, ролей або ідентифікації.

### Categories
Без категорій інформація не може бути організована в зрозумілу структуру.

### Objects
Objects — це центральний модуль знань і даних системи. Через нього описуються всі сутності, які можуть існувати в MAKiTRA: від простих нотаток до транспортних засобів, документів, фінансових операцій або активів.

### Важливий принцип
Finance, Notes, Vehicles, Assets, Documents та інші модулі не є окремим фундаментом. Вони мають будуватися поверх Objects і спеціалізуватися на конкретних типах інформації або сценаріях використання.

## 6. Roadmap

### Версія 0.2
- закріплення поточної моделі доступу;
- розширення базового User flow;
- розвиток Categories як базового шару структурування;
- підготовка до введення Objects як центральної моделі.

### Версія 0.3
- впровадження Objects як центральної моделі системи;
- перший варіант універсальних об’єктів із властивостями й категоріями;
- початок роботи з базовими зв’язками між об’єктами;
- розширення логіки для повторюваних сценаріїв.

### Версія 0.4
- розвиток Finance поверх Objects;
- базова підтримка фінансових операцій і зв’язків з іншими об’єктами;
- початок формування аналітичного шару.

### Версія 0.5
- розвиток Notes поверх Objects;
- підтримка неструктурованої та напівструктурованої інформації;
- інтеграція з Categories і Objects.

### Версія 0.6
- розвиток Vehicles поверх Objects;
- підтримка спеціалізованих об’єктів із власними властивостями;
- розширення моделі для різних класів даних.

### Версія 0.7
- розвиток Assets поверх Objects;
- підключення додаткових типів сутностей до єдиного ядра;
- поглиблення роботи з пов’язаними даними.

### Версія 0.8
- розширення Statistics;
- базова аналітика, агрегати, звіти, показники поверх Objects.

### Версія 0.9
- стабілізація системи як цілісного продукту;
- уточнення прав, ролей, безпеки й поведінки модулів;
- підготовка до розширення інтерфейсів.

### Версія 1.0
- повноцінна персональна інформаційна система;
- ядро даних, модулі, інтерфейс і правила роботи працюють як єдина система;
- MAKiTRA готова до довгострокового використання як основний цифровий простір користувача.

## 7. Що принципово НЕ робити зараз

Наразі не потрібно робити наступне:

- не вводити ORM;
- не переходити на PostgreSQL;
- не додавати Redis;
- не вводити DI framework;
- не розбивати систему на мікросервіси;
- не створювати складні абстракції без потреби;
- не перетворювати Telegram на основний шар системи;
- не розвивати нові модулі без підтримки базового ядра.

Це важливо для збереження простоти, контролю та поступовості розвитку. MAKiTRA має рости як система з чітким ядром, а не як набір незалежних експериментів.

## Підсумок

MAKiTRA — це довгострокова концепція персональної інформаційної системи, яка має стати центром управління особистими даними, задачами, активами, фінансами, нотатками й іншими сутностями. Поточний проєкт є лише початком цієї дорожньої карти.

Успіх MAKiTRA полягає не в тому, щоб швидко розширити функціональність, а в тому, щоб поступово збудувати надійне ядро, яке зможе підтримувати зростання без втрати структури і ясності.
